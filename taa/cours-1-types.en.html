Part 1

Why an abstract type

There are two ways to design an algorithm. The first: code right away with the types of the language (arrays, records…) and their functions. The algorithm is then glued to that language, and hard to transcribe into another one.

The second: define an abstract type first. You give the type a name, list what can be done with it and the properties those operations obey, without saying anything about the language or the machine. If a problem needs a stack, you reason with “push” and “pop”, without wondering whether the stack is an array or a chain of cells in memory.

Key points

The definition of an abstract algebraic type (or abstract data type) is made of two parts:

  • a signature: the types and the operations;
  • a system of axioms: the properties of those operations.

The rest of the course follows the same plan. Here is the skeleton of a definition, with its six keywords in order:

types
    the types we define
uses
    the types that already exist
operations
    name : types of the arguments → type of the result
preconditions
    the domain of the partial operations
axioms
    the properties of the operations
with
    the type of each name used in the axioms
Why it is useful

The axioms are enough to compute. In the workshop at the top of the page, the term top(pop(push(push(emptystack, a), b))) reduces to a just by applying two axioms, with no stack in memory.

Part 2

The signature: types and operations

The signature of an abstract type is made of types and operations.

The types are names of sets of values: the ones you want to define. You list them after the keyword types, for example stack, list, graph.

Each operation is defined by its name and its profile: the types of its arguments, then, after the arrow, the type of its result.

operations
    delete : list x integer → list
    length : list → integer
       nth : list x integer → element
       _^_ : integer x integer → integer
     false : → boolean
OperationArgumentsResultHow you write it
deletea list, an integera listdelete(λ, i)
lengtha listan integerlength(λ)
_^_two integersan integer4^2: each _ marks the place of an argument (infix notation)
falsenonea booleanfalse: it is a constant
Key points
  • The definition of an operation = its name + its profile.
  • The profile reads “types of the arguments → type of the result”. The symbol × separates the arguments.
  • A constant is an operation with no argument: nothing before the arrow. It returns a value of the defined type: emptystack : → stack in the stack type, false : → boolean in the boolean type.
In the exam

2023 midterm: “What type of data does a constant return?” Expected answer: a defined type. A paper that answered “predefined” got 0: the sheet’s example false : → boolean is the constant of the boolean type itself.

Trap

The profile does not say what the operation does. push : stack × element → stack and pop : stack → stack both return a stack: the axioms say which one adds and which one removes.

Part 3

The hierarchy: defined and predefined types

An abstract type almost always builds on other types. A list contains elements, is measured with integers, is tested with booleans. So we distinguish two kinds of types:

Defined type

It is new, “under design”. It is the one you are writing. It is listed in types.

E.g.: list, box in the list type.

Predefined type

It already exists, “already designed”. You use it without redefining it. It is listed in uses, before the operations.

E.g.: integer, boolean, element.

types
    list, box
uses
    integer, element

Here, the iterative list defines two types at once: the list and the box (the cell that holds an element). It uses integers (for ranks) and elements (what you store), which already exist.

Key points

Defined = in types, the new one. Predefined = in uses, it already exists. This distinction is used to classify the operations (next part).

The uses area is part of the signature: the exam answer keys name three areas for the signature, types, uses and operations. The preconditions, the axioms and the with area are not part of it.

Part 4

Internal operations and observers

Once the types are classified, the profile of an operation is enough to tell its role.

Internal operation

It returns a result of a defined type. It builds or modifies a piece of data of the type.

push : stack × element → stack

Observer

It has at least one argument of a defined type and returns a result of a predefined type. It queries the data without changing it.

top : stack → element

internal operationobserverconstant
types
    stack
uses
    boolean, element
operations
    emptystack : → stack
          push : stack x element → stack
           pop : stack → stack
           top : stack → element
       isempty : stack → boolean

Your turn: classify each operation. Hint: look at the type of the result first, then at whether there is an argument of a defined type.

Classic traps
  • “Observer” does not mean “returns a boolean”. top returns an element and it is an observer.
  • A defined type may not be the “main” type. In the iterative list, box is defined: access : list × integer → box is therefore an internal operation, whereas contents : box → element is an observer.
  • A constant like emptystack has no argument: it cannot be an observer, which needs an argument of a defined type. It returns the defined type: it is an internal operation with no argument.
In the exam

Course questions seen in the midterms: “What are the specifications of the profile of an observer?”, “The definition of an operation is made of?” Answer with the words of the course: at least one argument of a defined type, a result of a predefined type; a name and a profile.

Part 4 of 8
Part 5

Partial operations and preconditions

Some operations do not make sense everywhere. The top of an empty stack does not exist. You cannot delete the 5th element of a list that has 3. These operations are partial: they are defined only on part of their arguments.

The preconditions give this domain of definition, with the formula is-defined-iaoi (“is defined if and only if”). You write them before the axioms.

preconditions
    pop(s) is-defined-iaoi isempty(s) = false
    top(s) is-defined-iaoi isempty(s) = false
    delete(λ, i) is-defined-iaoi isempty(λ) = false & 1 ≤ i ≤ length(λ)
Method: is an operation partial?
  1. Look for an argument for which the result makes no sense: empty structure, rank out of bounds, cell never filled.
  2. If there is one, write the precondition that rules it out, with the operations of the type (isempty, length, ≠ emptylist…).
  3. Otherwise, the operation is total: no precondition, and say so.

To write a precondition, you sometimes need an operation that does not exist yet. To search for an element in a list, you first need to know whether it is there: you add ispresent to the signature, just to write the domain of search. An operation that serves to specify the domain of definition of another one is called an auxiliary operation.

operations
    ispresent : element x list → boolean
       search : element x list → box
preconditions
    search(e, λ) is-defined-iaoi ispresent(e, λ) = true
In the exam

2019 midterm: “an operation used to specify the domain of definition of another one” is an auxiliary operation; “an operation that is not defined everywhere” is a partial operation (2021, 2022). ispresent and search came up in 2018 and in 2020.

Trap

Do not invent a precondition. push works on any stack. Concatenating two lists works even if one of them is empty: at the 2023 midterm, the right answer to “preconditions of concatenate?” was none.

A precondition that is not met makes the term undefined. Try it: the workshop stops as soon as a partial operation receives an empty stack.

Part 6

The axioms: applying observers to internal operations

The profile says what an operation takes and returns, not what it does. The axioms give the properties. To find out what an internal operation does, you apply the observers to it: “if I push e, what is the top? Is the stack empty?”.

In practice, you make a table: each observer (and each operation that undoes, like pop) applied to each way of building a stack (emptystack, push(s, e)). Each cell gives an axiom, or nothing if a precondition forbids it.

emptystackpush(s, e)
isemptyisempty(emptystack) = trueisempty(push(s, e)) = false
topforbidden (precondition)top(push(s, e)) = e
popforbidden (precondition)pop(push(s, e)) = s
 
axioms
    pop(push(s, e)) = s
    top(push(s, e)) = e
    isempty(emptystack) = true
    isempty(push(s, e)) = false
with
    stack s
    element e

An axiom can have a condition, written before ⇒: the equality holds only if the condition does. This is essential when the result depends on a case. For the iterative list, the i-th element after a deletion depends on where i stands relative to k:

axioms
    1 ≤ i < k ⇒ nth(delete(λ, k), i) = nth(λ, i)
    k ≤ i ≤ length(λ) - 1 ⇒ nth(delete(λ, k), i) = nth(λ, i + 1)
    length(delete(λ, k)) = length(λ) - 1
Key points
  • The axioms define what the internal operations do: you apply their observers to them.
  • Every possible case must give a value; the cases forbidden by a precondition have no axiom.
  • The with area gives the type of each name used (stack s, element e).
Trap

An axiom is an equality between two terms of the same type. top(push(s, e)) = s is wrong twice: the value is wrong, and the types do not match (an element on one side, a stack on the other).

Part 7

Reading and rewriting a term

A term is a series of nested operations: push(push(emptystack, a), b) is the stack where you pushed a then b. You read it from the inside out: the innermost operation was done first.

To compute a term, you rewrite it: you look for a piece that has exactly the shape of the left-hand side of an axiom, replace it with the right-hand side, and start again until no axiom applies.

  1. Spot the pattern. pop(push(s, e)) applies to any piece of the form “pop of a push”, whatever the stack s and the element e.
  2. Match the variables. In pop(push(push(emptystack, a), b)), s is push(emptystack, a) and e is b.
  3. Replace. The right-hand side is s: the piece becomes push(emptystack, a).
  4. Check the conditions and the preconditions. An axiom with ⇒ applies only if its condition is true; a partial operation outside its domain makes the term undefined.

The same steps, on the term drawn as a tree: each operation is a node, its arguments are its children. Go one step at a time and watch the highlighted subtree (the pattern), the frames of s and e (the variables), then the replacement. You will see why top, at the root, can do nothing until the pop below it is reduced.

Trap

An axiom applies to a piece that has exactly its shape. top(pop(push(push(emptystack, a), b))) does not have the form top(push(…)): you must first reduce the pop inside.

Part 8

Consistency, completeness and two full examples

The set of axioms of a type must have two properties:

Consistency

No contradictory axioms: you must never be able to prove two different results for the same term.

Adding top(push(s, e)) = first(s) next to top(push(s, e)) = e would make the stack inconsistent.

Completeness

Having written enough axioms: every well-defined term must be computable.

Without isempty(emptystack) = true, we could not compute isempty(emptystack).

Example 1: the boolean type

This is the application exercise from Moodle: write the axioms of not, _ and _ and _ or _. You apply each operation to the two constants true and false; for and and or, looking at the first argument is enough.

types
    boolean
operations
       true : → boolean
      false : → boolean
        not : boolean → boolean
    _ and _ : boolean x boolean → boolean
     _ or _ : boolean x boolean → boolean
axioms
    not(true) = false
    not(false) = true
    true and b = b
    false and b = false
    true or b = true
    false or b = b
with
    boolean b

Six axioms, and that is complete: every boolean term reduces to true or to false. Check it in the workshop.

Example 2: the vector type (Moodle appendix)

A vector has bounds and cells that you fill one by one. It brings back the whole chapter: a partial operation (nth) and conditional axioms that separate “same cell” and “other cell”.

types
    vector
uses
    integer, boolean, element
operations
          vect : integer x integer → vector
     modifynth : vector x integer x element → vector
           nth : vector x integer → element
        isinit : vector x integer → boolean
    upperlimit : vector → integer
    lowerlimit : vector → integer
preconditions
    nth(v, i) is-defined-iaoi lowerlimit(v) ≤ i ≤ upperlimit(v) & isinit(v, i) = true
axioms
    lowerlimit(v) ≤ i ≤ upperlimit(v) ⇒ nth(modifynth(v, i, e), i) = e
    lowerlimit(v) ≤ i ≤ upperlimit(v) & lowerlimit(v) ≤ j ≤ upperlimit(v) & i ≠ j
                ⇒ nth(modifynth(v, i, e), j) = nth(v, j)
    isinit(vect(i, j), k) = false
    lowerlimit(v) ≤ i ≤ upperlimit(v) ⇒ isinit(modifynth(v, i, e), i) = true
    lowerlimit(v) ≤ i ≤ upperlimit(v) & lowerlimit(v) ≤ j ≤ upperlimit(v) & i ≠ j
                ⇒ isinit(modifynth(v, i, e), j) = isinit(v, j)
    lowerlimit(vect(i, j)) = i
    lowerlimit(modifynth(v, i, e)) = lowerlimit(v)
    upperlimit(vect(i, j)) = j
    upperlimit(modifynth(v, i, e)) = upperlimit(v)
with
    vector v
    integer i, j, k
    element e
The “same cell, other cell” pattern

After modifynth(v, i, e), cell i holds e and all the other cells j ≠ i are unchanged. This split into two cases comes back in almost every axiom for access by position.

Typo on the Moodle page

The last of the three axioms on isinit is written there with init(v, j), an operation that does not exist. Read it as isinit(v, j), as above.

Stack or queue: everything is decided at the exit.

A stack and a queue receive their elements the same way, one at a time. What changes is which one comes out: the last one in for the stack, the first one in for the queue. You write their abstract types, you compute their terms, then you move on to sets, where order no longer matters.

Part 1

The stack: last in, first out

Think of a pile of plates. You put a plate on top. You take back the one on top. The ones underneath stay stuck until you have removed the ones above them.

A stack stores elements the same way. It is a LIFO structure (Last In, First Out): the last one in is the first one out. Entries and exits happen on the same side, at the top.

You only see the top

The only accessible element is the one on top: the top. An empty stack has no top.

You only remove the top

That is the operation pop. You cannot pop an empty stack.

You add on top

That is the operation push: the added element becomes the new top.

Try it. Push, pop, ask for the top. Under the stack, the bench writes the same state as a term: each push adds a layer around the previous stack.

The stack where a, then b, then c were pushed is written push(push(push(emptystack, a), b), c). The top c is in the outermost push call. The bottom, a, is the most deeply buried, right next to emptystack. Keep this picture in mind: it explains the whole difference with the queue (part 5).

What is it for? The summary sheet gives three uses:

  • reversing the order of elements: what goes in as a, b, c comes out as c, b, a (check it in the bench at the top of the page);
  • evaluating expressions;
  • simulating the call stack, to make a recursive algorithm iterative.
Key points
  • Stack = LIFO: last in, first out. You go in and out on the same side.
  • Only the top is accessible. You add with push, you remove with pop.
  • In a term, the top is the element of the outermost push call.
Trap

pop does not return the removed element: it returns the stack without its top (pop : stack → stack). To know the element, use top, which changes nothing in the stack. In some languages a single function does both: not here.

In the exam

The TAA exams of 2023 and 2024 contained neither stacks nor queues: their exercises were about lists. But according to Moodle, the MiMos on stacks and queues of the week of 19 October are “assumed known from the following Monday”: so they can come up in the exam of the week of 26 October. The stack abstract type

Here is the complete definition, as Moodle gives it. You will recognize the six keywords of chapter 1. The colors show the role of each operation.

internal operationobserverconstant
types
    stack
uses
    boolean, element
operations
    emptystack : → stack
          push : stack × element → stack
           pop : stack → stack
           top : stack → element
       isempty : stack → boolean
preconditions
    pop(s) is-defined-iaoi isempty(s) = false
    top(s) is-defined-iaoi isempty(s) = false
axioms
    pop(push(s, e)) = s
    top(push(s, e)) = e
    isempty(emptystack) = true
    isempty(push(s, e)) = false
with
    stack s
    element e

The summary sheet writes sort Stack in place of types stack: both mean the type being defined.

top and pop make no sense on an empty stack: they are partial operations. Their preconditions restrict them to the stacks such that isempty(s) = false. The two other operations are there “as always”: one to initialize, emptystack, and one to know whether the structure contains elements, isempty.

How to find the four axioms

The axioms say what the internal operations do; to find out, you apply the observers to them (sheet “Abstract types”). Every stack is built with emptystack and push(s, e): the stack that contains a then b is push(push(emptystack, a), b).

So you apply the observers isempty and top, and the operation pop, which undoes what push does, to these two shapes. Six cells: each gives an axiom, or nothing if a precondition forbids it.

Your turn: guess each cell, then click to check.

emptystackpush(s, e)
isempty isempty(emptystack) = true isempty(push(s, e)) = false
top nothing: the precondition forbids it top(push(s, e)) = e
pop nothing: the precondition forbids it pop(push(s, e)) = s

Four cells filled, four axioms. None has a condition: in push(s, e), the top is always e, whatever the stack s underneath.

Key points
  • Two partial operations, pop and top: defined if and only if isempty(s) = false.
  • Four axioms without conditions: pop(push(s, e)) = s, top(push(s, e)) = e, isempty(emptystack) = true, isempty(push(s, e)) = false.
  • No axiom for top(emptystack) or pop(emptystack): the preconditions forbid them.
Trap

Do not put a condition isempty(s) = false in front of the stack axioms. pop(push(s, e)) = s is true even if s is empty: pop(push(emptystack, a)) = emptystack. The precondition applies to the argument of pop, here push(s, e), which is never empty.

Part 3

Evaluating a stack term

You are given a term; you compute it with the axioms alone. Take top(pop(pop(push(push(push(emptystack, a), b), c)))). You push a, b, c, you pop twice, then you ask for the top. Intuitively, it is a. The axioms must confirm it.

  1. Read from the inside out. The most deeply buried operation was done first: three push, then two pop, then top.
  2. Spot “pop of a push”. The innermost pop applies to push(push(push(emptystack, a), b), c). The axiom pop(push(s, e)) = s cancels it: what remains is push(push(emptystack, a), b).
  3. Start again. The second pop now applies to push(push(emptystack, a), b): what remains is push(emptystack, a).
  4. Conclude. top(push(emptystack, a)) = a, by the axiom top(push(s, e)) = e.
Why from the inside

The stack axioms only talk about emptystack and push(s, e). None starts with top(pop(…)) or pop(pop(…)). So you must first make the inner pops disappear, until you land on a push again.

Check it in the workshop. The preset “push after a pop” finishes in a single step: top(push(s, e)) = e applies right away, without computing the stack s (here pop(push(push(emptystack, a), b)), which is well defined). You can also write your own terms.

Key points
  • “pop of a push” cancels out: pop(push(s, e)) = s.
  • “top of a push” gives the pushed element: top(push(s, e)) = e.
  • isempty is true on emptystack and false on any push.
Trap

A pop or a top applied to an empty stack makes the whole term undefined, even if the rest can be computed. Check the preconditions as you go: in the preset “undefined”, the first pop leaves emptystack, and the second is no longer allowed to apply.

Part 4

The queue: first in, first out

Think of a waiting line. If nobody cuts in line, the first person to arrive is the first to leave. Newcomers take their place at the end.

A queue is a FIFO structure (First In, First Out): the first one in is the first one out. Entries and exits each happen at one end: you enter at the back (the last one) and you leave at the front (the first one, also called the head).

You only see the first

The only accessible element is the first. An empty queue has no first.

You only remove the first

That is the operation dequeue, possible only if the queue is not empty.

You add at the back

That is the operation enqueue: the element is placed at the end, behind all the others.

Try it. Enqueue, dequeue, ask for the first, and watch the term under the queue.

In the term enqueue(enqueue(enqueue(emptyqueue, a), b), c), the element enqueued first, a, is the most deeply buried, right next to emptyqueue. Yet it is the first of the queue. This is the opposite of the stack, where the accessible element is on the outside of the term.

What is it for? According to the summary sheet:

  • keeping the order of elements: what goes in as a, b, c comes out as a, b, c;
  • implementing “buffers”, waiting lines: printer, keyboard…;
  • traversing trees, graphs… breadth-first.

  • You add at the back with enqueue, you remove at the front with dequeue; only the first is accessible.
  • In a term, the first is the element of the most deeply buried enqueue call.
Trap

The first of the queue is not the last element written in the term. In enqueue(enqueue(enqueue(emptyqueue, a), b), c), the first is a, not c: c has just arrived, it waits behind the others.

Part 5

The queue abstract type: conditional axioms

The signature of the queue has exactly the same shape as that of the stack: only the names change. So do the preconditions: dequeue and first are partial, since an empty queue has neither a first nor an element to remove.

types
    queue
uses
    boolean, element
operations
    emptyqueue : → queue
       enqueue : queue × element → queue
       dequeue : queue → queue
         first : queue → element
       isempty : queue → boolean
preconditions
    dequeue(q) is-defined-iaoi isempty(q) = false
    first(q) is-defined-iaoi isempty(q) = false
Typo in the sheet

In the summary sheet “Queues”, the defined type is written sort Stack. Read sort Queue, as in all the profiles that follow.

The first is at the bottom of the term

Stack: the top is outside

push(push(push(emptystack, a), b), c)

The top is in the push call that is outermost. In push(s, e), the top is always e, whatever s is.

Queue: the first is at the bottom

enqueue(enqueue(enqueue(emptyqueue, a), b), c)

The first is in the enqueue call that is most deeply buried, the one that touches emptyqueue. In enqueue(q, e), e has just arrived: it is the first only if q is empty.

Why the queue needs conditions and the stack does not

For the stack, the element concerned by top and pop is always e, the last one pushed: the result does not depend on s, a single formula is enough.

For the queue, what comes out of enqueue(q, e) depends on q. If q is empty, e is alone: it is the first, and dequeue removes it. Otherwise, the first is somewhere at the bottom of q, and e changes nothing there. Two cases, so two axioms for first and two for dequeue, each preceded by its condition: isempty(q) = true ⇒ … or isempty(q) = false ⇒ ….

Your turn: fill in the same table as for the stack, then check.

emptyqueueenqueue(q, e)
isempty isempty(emptyqueue) = true isempty(enqueue(q, e)) = false, without condition
first nothing: the precondition forbids it two cases: e if isempty(q) = true; first(q) if isempty(q) = false
dequeue nothing: the precondition forbids it two cases: emptyqueue if isempty(q) = true; enqueue(dequeue(q), e) if isempty(q) = false

This gives the six axioms of Moodle. The four conditional axioms are highlighted.

axioms
    isempty(q) = true ⇒ first(enqueue(q, e)) = e
    isempty(q) = false ⇒ first(enqueue(q, e)) = first(q)
    isempty(q) = true ⇒ dequeue(enqueue(q, e)) = emptyqueue
    isempty(q) = false ⇒ dequeue(enqueue(q, e)) = enqueue(dequeue(q), e)
    isempty(emptyqueue) = true
    isempty(enqueue(q, e)) = false
with
    queue q
    element e

Reading dequeue(enqueue(q, e)) = enqueue(dequeue(q), e)

This is the trickiest axiom of the chapter. It applies when q is not empty, and reads in three steps:

  1. Set e aside. In enqueue(q, e), e is the last to arrive: since q is not empty, it is not the one that leaves.
  2. Dequeue q. The first of the whole queue is the first of q: dequeue(q) removes it.
  3. Put e back at the end. enqueue(dequeue(q), e): e takes its place again, at the back.

On the queue a, b, c, the dequeue thus goes down one level at each step, down to the enqueue call that touches emptyqueue. There, the case “q empty” applies, and a disappears:

  1. dequeue(enqueue(enqueue(enqueue(emptyqueue, a), b), c))
  2. enqueue(dequeue(enqueue(enqueue(emptyqueue, a), b)), c)
    q = enqueue(enqueue(emptyqueue, a), b) is not empty: we set c aside and we dequeue q.
  3. enqueue(enqueue(dequeue(enqueue(emptyqueue, a)), b), c)
    Same case one level down: q = enqueue(emptyqueue, a) is not empty, we set b aside.
  4. enqueue(enqueue(emptyqueue, b), c)
    Finally q = emptyqueue: dequeue(enqueue(emptyqueue, a)) = emptyqueue. The queue b, c remains.

It remains to see why the axiom is true. When q is not empty, enqueuing e then dequeuing, or dequeuing then enqueuing e, gives the same queue: in both orders, it is the first of q that leaves. Compare the two columns, then choose “q empty”: the right-hand side no longer exists, hence the condition.

Key points
  • Six axioms: four conditional (first and dequeue on enqueue(q, e), depending on whether q is empty or not) and two without condition for isempty.
  • The two conditions isempty(q) = true and isempty(q) = false cover all the cases: no gap, no contradiction.
  • The reason: in the term, the first one in is the most deeply buried.
Trap

dequeue(enqueue(q, e)) = q is the axiom of the stack. For the queue, it is correct only if q is empty (and then q = emptyqueue). As soon as q contains an element, it is the first of q that leaves, not e.

Part 6

Evaluating a queue term

The method is the one for the stack, with one more reflex: before applying an axiom to enqueue(q, e), compute isempty(q) to choose the right case.

  1. Spot the pattern. first(enqueue(q, e)) or dequeue(enqueue(q, e)). As for the stack, first reduce the inner dequeues that do not have this shape.
  2. Compute isempty(q). false if q is written enqueue(…), true if q is emptyqueue. If q contains a dequeue, reduce it first.
  3. Apply the axiom of the right case. Empty case: e for first, emptyqueue for dequeue. Non-empty case: first(q), or enqueue(dequeue(q), e).
  4. Start again until the final form. first and dequeue thus go down to the bottom of the term.

Stack and queue on the same elements

Put a, b, c, in that order, into a stack and into a queue, then count the computation steps (redo them in both workshops).

Stack

push(push(push(emptystack, a), b), c)
  • top = c: 1 step.
  • pop → push(push(emptystack, a), b): 1 step.
  • Order of exit: c, b, a.

Queue

enqueue(enqueue(enqueue(emptyqueue, a), b), c)
  • first = a: 3 steps.
  • dequeue → enqueue(enqueue(emptyqueue, b), c): 3 steps.
  • Order of exit: a, b, c.

The stack answers in one step, because its accessible element is on the outside of the term. The queue has to go down to the bottom: one step per element traversed.

Key points
  • On a queue written with enqueue around emptyqueue, first gives the element of the innermost enqueue call.
  • dequeue removes this innermost call and keeps the others in the same order.
  • A first or a dequeue on an empty queue makes the term undefined, as for the stack.
Trap

The condition is about q, and q can be a complicated term. In first(enqueue(dequeue(enqueue(emptyqueue, a)), b)), q = dequeue(enqueue(emptyqueue, a)): you have to reduce it to see that it equals emptyqueue. So isempty(q) = true, and the first is b (preset “q to reduce first”).

Part 7

Sets: only presence counts

Bonus

In the Moodle planning of the MiMos, sets are presented as a “bonus”. The official plan of the ECUE also stops at the sequential types: lists, stacks and queues. Keep these last two parts for when stacks and queues are solid.

In a list, a stack or a queue, the order of the elements is fundamental. In a set, it does not matter at all. Only one thing counts: an element is present or not.

Adding a then b, or b then a, gives the same set. Adding a a second time changes nothing.

The base: the empty set and membership

types
    set
uses
    element, boolean
operations
    emptyset : → set
         _∈_ : element × set → boolean
axioms
    x ∈ emptyset = false

_∈_ is written between its two arguments: x ∈ s. Each _ marks the place of an argument, as for _^_ in chapter 1. In all the axioms that follow, x and y are elements and s is a set.

Add, delete, count

We must also be able to add and delete an element. The sheet makes a choice: these operations have no effect in case of error. Adding an element that is already present does nothing; deleting an absent element does nothing either. add and delete are therefore defined everywhere: no precondition.

On top of that comes the observer card, the number of elements of the set, also defined everywhere.

operations
       add : element × set → set
    delete : element × set → set
      card : set → integer
axioms
    x = y ⇒ (x ∈ add(y, s)) = true
    x ≠ y ⇒ (x ∈ add(y, s)) = (x ∈ s)
    x = y ⇒ (x ∈ delete(y, s)) = false
    x ≠ y ⇒ (x ∈ delete(y, s)) = (x ∈ s)
    card(emptyset) = 0
    x ∈ s = true ⇒ card(add(x, s)) = card(s)
    x ∈ s = false ⇒ card(add(x, s)) = card(s) + 1
    x ∈ s = true ⇒ card(delete(x, s)) = card(s) − 1
    x ∈ s = false ⇒ card(delete(x, s)) = card(s)

The axioms of ∈ separate two cases, like those of the vector in chapter 1: the tested element is the one we have just added or deleted (x = y), or it is another one (x ≠ y), which the operation does not concern.

Those of card separate “already present” and “absent”: this is where the choice “no effect in case of error” shows.

Typos in the sources
  • On the Moodle page, the axiom of card(delete(x, s)) for an absent element is written with x ∈ = false: the set is missing. Read x ∈ s = false.
  • In the PDF sheet, the first two axioms of card are stuck together on a single line. They are indeed two axioms: card(emptyset) = 0, then the one for card(add(x, s)).

Choosing an element

To apply the same treatment to all the elements, you enumerate: you choose an element, you process it, then you start again on the set obtained by deleting the processed element. This requires a choice operation.

operations
    choose : set → element
preconditions
    choose(s) is-defined-iaoi s ≠ emptyset
axioms
    choose(s) ∈ s = true

choose is partial: in an empty set, there is nothing to choose. Its only axiom just says that the chosen element belongs to the set, not which one. That is why the workshop below does not use it: there is nothing to compute.

Key points
  • Set: an element is present or absent; order and repetitions do not count.
  • add and delete have no precondition: no effect in case of error.
  • card only increases if the added element was absent, and only decreases if the deleted element was present.
  • choose is partial: defined if and only if s ≠ emptyset.
Trap

card(add(x, s)) is not always card(s) + 1: if x is already in s, the cardinality does not move (preset “a added twice”). Test x ∈ s first.

Part 8

Multisets: when repetitions count

A multiset, or family, is a set that accepts multiple occurrences of an element. Adding a twice gives two a. The order, for its part, still does not count.

We keep the same operations, but their behavior changes. Adding an element that is already present increases the number of elements. Deleting an element does not necessarily make it disappear: other occurrences may remain. Hence one more operation, nboccurrences, which counts the occurrences of an element.

types
    multiset
uses
    element, boolean, integer
operations
    emptymultiset : → multiset
              add : element × multiset → multiset
           delete : element × multiset → multiset
              _∈_ : element × multiset → boolean
             card : multiset → integer
    nboccurrences : element × multiset → integer
axioms
    (x ∈ emptymultiset) = false
    x = y ⇒ (x ∈ add(y, ms)) = true
    x ≠ y ⇒ (x ∈ add(y, ms)) = (x ∈ ms)
    nboccurrences(x, ms) ≤ 1 ⇒ (x ∈ delete(x, ms)) = false
    x ≠ y ⇒ (x ∈ delete(y, ms)) = (x ∈ ms)

    card(emptymultiset) = 0
    card(add(x, ms)) = card(ms) + 1
    x ∈ ms = true ⇒ card(delete(x, ms)) = card(ms) − 1
    x ∈ ms = false ⇒ card(delete(x, ms)) = card(ms)

    nboccurrences(x, emptymultiset) = 0
    x = y ⇒ nboccurrences(x, add(y, ms)) = nboccurrences(x, ms) + 1
    x ≠ y ⇒ nboccurrences(x, add(y, ms)) = nboccurrences(x, ms)
    nboccurrences(x, ms) = 0 ⇒ nboccurrences(x, delete(x, ms)) = 0
    nboccurrences(x, ms) ≥ 1 ⇒
            nboccurrences(x, delete(x, ms)) = nboccurrences(x, ms) − 1
    x ≠ y ⇒ nboccurrences(x, delete(y, ms)) = nboccurrences(x, ms)
Typo on the Moodle page

The profile of nboccurrences is written there element × multiset → element. The operation counts occurrences: it returns an integer, as the PDF sheet writes it (and as its axioms show: = 0, + 1).

The key point is card(add(x, ms)) = card(ms) + 1: the condition has disappeared, since every addition counts. Conversely, the axiom of ∈ on delete gains one: after the deletion, x is absent only if it had at most one occurrence before.

The axioms of nboccurrences follow the pattern of ∈: either the operation touches x itself (x = y, or delete(x, ms)), or it touches another element (x ≠ y) and the count of x does not move. For the deletion of x itself, two cases: if there was none, there is still none; if there was at least one, there is one fewer.

Remark

The sheet gives no axiom for x ∈ delete(x, ms) when x has at least two occurrences in ms. Its text does settle the case, though: deleting an element “does not imply that it disappears from the set (if there are several occurrences)”. So x is still present.

Key points
  • Multiset (family) = a set that accepts multiple occurrences.
  • nboccurrences : element × multiset → integer counts the occurrences of an element.
  • Every add increases card by 1, without condition.
  • delete removes a single occurrence: x stays present if it had several.
Trap

Do not copy the axioms of the set. x ∈ s = true ⇒ card(add(x, s)) = card(s) is false for a multiset: card(add(a, add(a, emptymultiset))) is 2, not 1 (preset “a added twice”, in both workshops).
